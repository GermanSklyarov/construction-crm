# construction-crm — «Объекты и задачи»

Мини-CRM строительной компании, тестовое задание 2B Studio. Постановщик управляет объектами и задачами, назначает исполнителей, принимает работу или возвращает её с комментарием. Исполнитель видит только свои задачи и связанные стройки.

**Демо:** https://construction-crm-wine.vercel.app

**Репозиторий:** https://github.com/GermanSklyarov/construction-crm

В Supabase Cloud подготовлены один постановщик (`manager1`) и два исполнителя (`executor1`, `executor2`), три объекта и три задачи в разных статусах. Это обозначения ролей демо, а не логины: email и пароли передаются работодателю отдельно, в репозитории их нет.

## Возможности и безопасность

- Вход по email/паролю; список и карточка объекта; карточка задачи с историей; «Мои задачи».
- Создание, правка, назначение и удаление объектов/задач постановщиком; подтверждение удаления задачи.
- Статусы: новая → в работе → на проверке → принята; возврат на доработку требует комментария, после него исполнитель снова берёт задачу в работу.
- RLS в PostgreSQL ограничивает доступ даже при прямых запросах. Статус меняется только через `transition_task`; история записывается автоматически и недоступна для прямого изменения через пользовательский API.
- `row_version` предотвращает сохранение/удаление устаревших данных. Интерфейс обрабатывает потерю доступа, конфликты и сетевые ошибки.
- Регистрация и анонимный вход отключены. В браузере только публичный Supabase key; роль берётся из `profiles`, а не из редактируемых metadata.

## Стек и архитектура

React + TypeScript + Vite; React Router; TanStack Query; React Hook Form + Zod; Tailwind CSS, Radix UI/компонент Button по подходу shadcn/ui. Supabase JS Client обращается непосредственно к Supabase Auth и Data API; отдельного прикладного сервера нет. PostgreSQL отвечает за права, ограничения, переходы и историю. Frontend опубликован на Vercel.

| Путь | Назначение |
| --- | --- |
| `src/main.tsx` | Инициализация приложения, вход и сессия |
| `src/workspace.tsx` | Маршруты, экраны, запросы и действия |
| `src/forms.tsx`, `src/domain.ts` | Формы, валидация, доступные действия и сообщения ошибок |
| `src/db.ts`, `src/ui/`, `src/style.css` | Типизированный клиент, UI и стили |
| `supabase/migrations/` | Схема, RLS, RPC, история и версии строк |
| `supabase/tests/`, `scripts/`, `e2e/` | Проверки БД, API, конкурентности, окружения и браузерных сценариев |
| `vercel.json` | Vite build, каталог `dist`, SPA fallback |

Подробно: [модель данных и безопасность](docs/database-security.md), [решения и ограничения](docs/handoff/decisions.md).

## Локальный запуск

Нужны Node.js **24.x**, npm и Docker. Supabase CLI закреплён в devDependencies. В репозитории:

```sh
npm ci
npm run db:start
npx supabase migration up
npm run demo:prepare
npm run dev
```

`demo:prepare` работает только с локальным Supabase: создаёт/восстанавливает четыре аккаунта (два постановщика и два исполнителя), три объекта и три задачи. Настраивает `.env.local`, сохраняет случайные пароли в игнорируемом `.local/demo.json` с правами 0600; повтор использует те же пароли. Восстанавливаются только задачи с выделенными ID, остальные задачи сохраняются. Файл содержит локальные доступы, его нельзя публиковать. Облачные аккаунты этим скриптом не обслуживаются.

Frontend обычно доступен на `http://localhost:5173`, Studio — `http://127.0.0.1:54323`, API — `http://127.0.0.1:54321`. Если демо не нужно, скопируйте `.env.example` в `.env.local` и настройте публичные URL/key вручную; Auth-пользователя и профиль создаёт администратор.

`npm run db:stop` останавливает локальные сервисы. `npm run db:reset` удаляет локальные данные и пересоздаёт БД — для обычного запуска не требуется. Не запускайте reset или тестовые seed-скрипты против Cloud.

## Переменные и миграции

| Переменная frontend | Локально | Vercel Production |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | `http://127.0.0.1:54321` | `https://ahujrrwzxfopkbysxucz.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ локального проекта | Publishable key Cloud-проекта |

Vite встраивает значения при сборке. `.env.local` загружается и при build; `.env.production.local` может переопределить его, поэтому перед локальной сборкой проверьте выбранное окружение. Не добавляйте secret/service_role, пароли и CLI-токены в `VITE_*`. Build-проверка разрешает только нужные переменные и явный список публичных метаданных Vercel.

Миграции применяются последовательно: `20261104000000_initial.sql`, затем `20261105000000_row_version.sql`. Обе уже применены в Cloud. Supabase CLI v3 требует явного `--remote` для удалённых команд. Не переигрывайте миграции через SQL Editor и не переписывайте применённые файлы. [Инструкция развёртывания](docs/deployment/README.md) содержит проверку истории, dry-run и безопасный порядок применения к новому проекту.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
npm run test:deployment
npm run test:demo
npm run build
```

С запущенным **локальным** Supabase:

```sh
npm run db:test
npm run db:lint
npm run db:test:concurrency
npm run db:test:api
npm run test:e2e
```

E2E используют настоящий установленный Google Chrome, отдельный Vite на порту 5174 и подготовленные локальные данные. Скриншоты/отчёты игнорируются Git. `npm run db:check:migrations` дополнительно проверяет чистые прикладные схемы и SQL демо в локальной транзакции с откатом; на время проверки блокирует таблицы.

Результаты и границы: [этап 3](docs/stage-3-report.md), [финальная production-проверка](docs/stage-4-report.md). Локально проверены RLS, RPC, конфликты и полный браузерный цикл. Production: проверены загрузка, прямые ссылки до входа, конфигурация, публичный запрет доступа и наличие демоданных; проверка UI под тремя пользователями ещё требует отметок владельца.
