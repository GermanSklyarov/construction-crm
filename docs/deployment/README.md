# Deployment & Handoff — подготовка

Текущее состояние: Cloud-проект `ahujrrwzxfopkbysxucz` создан, обе миграции применены, структура проверена, три профиля и демоданные созданы и проверены. Vercel ещё не опубликован. Разделы 1–3 сохранены как инструкция воспроизведения; повторно выполнять их в текущем проекте не нужно. Не запускайте блоки целиком: после каждого этапа сверяйте проект и результат.

## 1. Supabase Dashboard: действия владельца

1. Создайте **новый** проект в организации Free. Сохраните пароль БД в менеджере паролей; выберите подходящий регион. Не используйте существующий рабочий проект с данными.
2. Запишите Project Ref и Project URL `https://<project-ref>.supabase.co`. Для браузера скопируйте **publishable key** (`sb_publishable_...`) из API Keys. Secret/service_role key для этого развёртывания не требуется.
3. Authentication → настройки Sign In / Providers: выключите **Allow new users to sign up** и **Allow anonymous sign-ins**. Email/password provider оставьте включённым: иначе существующие пользователи не смогут войти. Не выключайте глобальное подтверждение email ради демо; подтвердите только созданные администратором аккаунты.
4. В Data API оставьте exposed schema `public`; `private` не публикуйте. После миграций проверьте RLS для всех четырёх таблиц.
5. После получения финального домена Vercel укажите его HTTPS URL в Authentication → URL Configuration → Site URL. Если нужны redirect URLs, добавляйте только конкретный доверенный адрес, без широких wildcard для preview-доменов. Приложение использует password login, не OAuth.

Настройки `supabase/config.toml` относятся к локальному окружению и автоматически в Cloud не переносятся. Не запускайте `supabase config push` для копирования локальной конфигурации.

[Настройки Auth](https://supabase.com/docs/guides/auth/general-configuration). Условия бесплатных тарифов проверьте перед созданием: [Supabase](https://supabase.com/pricing), [Vercel Hobby](https://vercel.com/docs/plans/hobby). Hobby предназначен для личного некоммерческого использования; демонстрацию не превращаем в рабочую систему работодателя. Перед интервью проверьте доступность проекта и текущие ограничения Free.

## 2. CLI и миграции — только после подтверждения

В репозитории закреплён Supabase CLI **3.0.0**. В v3 локальная БД — цель по умолчанию; hosted требует явного `--remote`. Не переносите команды v1/v2 с `--linked` без проверки справки.

```sh
npm ci
npx supabase --version
npx supabase login
# Интерактивный вход: не помещайте access token в команду, README или .env frontend.
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase migration list --remote=YOUR_PROJECT_REF
npx supabase db push --remote=YOUR_PROJECT_REF --dry-run --skip-vault
```

Замените `YOUR_PROJECT_REF` на ref именно нового проекта. Сверьте его с Dashboard перед каждым удалённым действием. CLI использует авторизованный доступ; если требуется пароль, вводите его интерактивно, не передавайте через `--password` в истории команд. Не включайте `--debug` и не публикуйте служебные логи. Не экспортируйте `SUPABASE_YES` и не используйте `--yes`.

На чистом проекте dry-run должен показать ровно две миграции:

1. `20261104000000_initial.sql` — таблицы, роли приложения, RLS, grants, история, RPC.
2. `20261105000000_row_version.sql` — версии строк и обновлённый RPC.

**Остановитесь и согласуйте применение.** После подтверждения:

```sh
npx supabase db push --remote=YOUR_PROJECT_REF --skip-vault
npx supabase migration list --remote=YOUR_PROJECT_REF
```

Обе версии должны присутствовать локально и удалённо. Не используйте `db reset --remote`, `--include-seed`, `--include-roles`, `migration repair` или `--include-all` для обхода неожиданной ошибки. Не вставляйте миграции через SQL Editor — это обходит историю CLI. При конфликте схемы/версий остановитесь и разберите причину.

Воспроизводимость: зависимости только от стандартного Supabase (`auth.users`, `auth.uid()`, роли anon/authenticated, PostgreSQL с `gen_random_uuid`). Локальная проверка `npm run db:check:migrations` успешно применила обе миграции на чистые **прикладные** схемы внутри транзакции, проверила RLS/grants и SQL-демо, затем выполнила ROLLBACK. Существующие локальные данные сохранены. Это не отдельный чистый Cloud-проект: системные Auth-схемы взяты из локального Supabase PostgreSQL 17. После этой локальной проверки обе миграции успешно применены к новому hosted-проекту; история CLI, таблицы, RLS, grants и RPC проверены запросами только на чтение. Миграции одноразовые, повторное применение тех же SQL напрямую не поддерживается; CLI учитывает историю.

[CLI v3: выбор цели](https://supabase.com/docs/guides/local-development/local-and-hosted-projects), [миграции](https://supabase.com/docs/guides/deployment/database-migrations).

## 3. Три облачных демоаккаунта и данные

Используем отдельный ручной путь, без локального `prepare-demo.mjs`:

1. После миграций создайте в Authentication → Users → Add user / Create user ровно три аккаунта: постановщик, исполнитель 1, исполнитель 2. Используйте отдельные адреса демо, не личные аккаунты сотрудников. Задайте разные случайные пароли (например, 20+ символов) в Dashboard; включите Auto Confirm для этих трёх пользователей. Сохраните пароли в менеджере паролей, передайте работодателю отдельно от публичной ссылки.
2. Скопируйте их UUID. В локальной копии [cloud-demo.sql](cloud-demo.sql) замените только три `REPLACE_*_UUID`. Копию храните в игнорируемой `.local/`, не в `supabase/migrations`. Проверьте соответствие UUID аккаунтам и ролям.
3. **После отдельного подтверждения записи демоданных** откройте SQL Editor именно нужного проекта и выполните весь шаблон одной транзакцией. В нём нет паролей, служебных ключей, удаления, upsert или изменения схемы. Он добавляет 3 профиля, 3 объекта и 3 задачи: новая / в работе / на проверке. Изменение статусов выполняется существующим RPC, история содержит 6 записей.
4. Если произошла ошибка, выполните `ROLLBACK;` в той же сессии SQL Editor и проверьте причину. Auth-пользователи создаются отдельно и сохраняются при ошибке SQL. Повтор SQL намеренно отклоняется при существующих профилях/ID и не сбрасывает данные. Для исправления не удаляйте аккаунты с рабочими связями и не меняйте миграции.

Локальный `prepare-demo.mjs` проверен отдельно: он жёстко ограничен loopback, получает локальный service_role, обновляет четыре аккаунта, восстанавливает локальные fixtures и переписывает `.env.local`. Для Cloud это неподходящий контракт. Не убирайте его проверку localhost и не запускайте локальные E2E/API seed-скрипты против облака. SQL-шаблон — доверенная административная инициализация, не доказательство RLS; проверку прав выполняют обычные пользователи после публикации.

## 4. Vercel: подготовка и будущий запуск

После настройки Supabase и отдельного разрешения на публикацию:

- Import Git Repository → личный Hobby-проект. Root Directory — корень репозитория.
- Framework Preset: Vite; Node.js: 24.x; Install: `npm ci`; Build: `npm run build`; Output: `dist`.
- В Environment Variables **Production** добавьте только:

| Имя | Значение | Секрет? |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | `https://<project-ref>.supabase.co` | Нет |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | publishable key этого проекта | Нет, публичный ключ защищён RLS |

Не добавляйте `service_role`, `sb_secret_...`, пароль БД, access token CLI и пароли демо ни в Vercel, ни в переменные с `VITE_`. Preview-переменные пока не задавайте: preview не должен незаметно работать с демонстрационными данными. Не добавляйте автоматическую Supabase-интеграцию, импортирующую лишние ключи.

Vite встраивает эти значения **при сборке**. Изменение переменных требует новой сборки/деплоя. `.env.local` в Git не хранится; локальная сборка может использовать локальный Supabase и не предназначена для ручной загрузки на Vercel. Build-проверка отклоняет недостающие значения, secret/service_role ключи, неизвестные `VITE_*` и localhost при `VERCEL=1`. Автоматические публичные `VITE_VERCEL_*` разрешены по явному списку в `scripts/check-build-env.mjs` (окружение, URL, Git-метаданные и hash salt). Отключать их автоматическую передачу Vercel не нужно. Произвольные `VITE_VERCEL_TOKEN`/`VITE_VERCEL_SERVICE_ROLE_KEY` не разрешены; secret-ключи Supabase и service_role JWT также отклоняются в значениях разрешённых метаданных, без вывода значений в ошибку. При добавлении Vercel нового поля сначала проверьте его назначение и расширьте список с тестом. Проверка не распознаёт любой возможный пароль — никогда не помещайте секреты в публичные метаданные, включая сообщения коммитов. Она проверяет формат, а не действительность ключа или его соответствие проекту — это проверяется входом после публикации.

Если сборка остановилась с `Unexpected VITE_ variable(s)`, новая диагностика перечисляет **только имена** отклонённых переменных, без значений. Пользовательские и интеграционные переменные смотрите в Vercel → проект → Settings → Environment Variables, с фильтром Production. Автоматические системные переменные могут не отображаться в этом списке. Для разбора достаточно имён и SHA коммита сборки; не раскрывайте значения и не печатайте `env`/`printenv` целиком. Не добавляйте неизвестное поле в allowlist без проверки источника и назначения.

Причина отказа Vercel CLI 65.11.0 на коммите `fbf58c0` подтверждена новым логом: в явном allowlist отсутствовали `VITE_VERCEL_DEPLOYMENT_ID`, `VITE_VERCEL_PROJECT_ID`, `VITE_VERCEL_GIT_PREVIOUS_SHA` и `VITE_VERCEL_OBSERVABILITY_CLIENT_CONFIG`. Добавлены только эти четыре имени. Первые три — идентификаторы/предыдущий Git SHA; последняя — публичные клиентские параметры Analytics/Speed Insights (URL скриптов и endpoints). Их разрешение не устанавливает SDK и не включает аналитику в приложении. Проверка значений на Supabase secret/service_role работает и для новых полей; неизвестные `VITE_*`, включая потенциальные токены Vercel, по-прежнему отклоняются. Регрессионные CLI-тесты воспроизводят именно четыре имени из лога, включая пустой предыдущий SHA первой сборки. Предупреждение npm о `cache-dir` не было причиной остановки.

Источники назначения переменных: [Vercel system variables](https://vercel.com/docs/environment-variables/system-environment-variables), [Analytics client config](https://vercel.com/docs/analytics/package), [Speed Insights client config](https://vercel.com/docs/speed-insights/package).

`vercel.json` содержит стандартный rewrite `/(.*)` → `/index.html` для React Router. Это обеспечивает загрузку SPA для `/tasks/<uuid>` и `/objects/<uuid>`; право читать данные по-прежнему проверяется RLS. `cleanUrls` не включён. На текущем этапе **не нажимайте Deploy**, не подключайте автоматические публикации и не запускайте Vercel CLI. После согласованной публикации добавьте полученный домен в Auth URL Configuration.

[Переменные Vite](https://vite.dev/guide/env-and-mode), [Vite SPA на Vercel](https://vercel.com/docs/frameworks/frontend/vite).

## 5. Перед отправкой в GitHub

```sh
git status --short --untracked-files=all
git diff --cached --stat
git check-ignore .env.local .local/demo.json .vercel/project.json supabase/.temp/project-ref
```

В `.gitignore` включены `.env*` (кроме пустого `.env.example`), `.local/`, `.vercel/`, CLI temp/branches, ключевые файлы, артефакты тестов. Ignore не удаляет ранее закоммиченные секреты: проверяйте staged diff перед push и используйте secret scanning GitHub. Не публикуйте вывод `supabase status -o json` — там есть служебные ключи. Если секрет когда-либо попал в историю, сначала отзовите его; удаления файла недостаточно. Оригинальный PDF сейчас untracked: перед публикацией решите, можно ли распространять задание работодателя.

- [ ] В двух сессиях постановщика проверить конфликт старой правки/удаления. Переназначить задачу: прежний исполнитель после обновления теряет доступ, новый получает.
- [ ] Создать временный объект/задачу через UI; редактировать; удалить задачу с подтверждением; проверить каскадное удаление истории; удалить пустой объект.

## Результаты подготовки

- Production build, typecheck, lint, 15 Vitest и 19 проверок build-env: PASS. JS bundle около 682 КБ / gzip 200 КБ; предупреждение Vite о размере остаётся.

- В tracked-файлах и доступной Git-истории не найдено совпадений по шаблонам Supabase secret/access tokens, JWT и private-key блоков. Это поиск известных форматов, не гарантия отсутствия всех возможных секретов. Credentials/CLI temp/Vercel metadata исключены из Git; tracked из env-файлов только `.env.example`.
