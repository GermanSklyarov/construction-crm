# Этап 1: Database & Security

Источник: оригинальное трёхстраничное PDF в корне проекта, прочитано целиком.
Уточнение заказчика имеет приоритет: физическое удаление задачи удаляет её историю.

## Схема

- `profiles`: UUID из `auth.users`, отображаемое имя, роль. Создание и изменение только через доверенное администрирование, не через пользовательский API. Не копируем роли из пользовательских metadata.
- `construction_objects`: UUID, название, адрес.
- `tasks`: UUID, название, описание, объект, исполнитель, статус, автор, дата создания. Составной FK `(assignee_id, assignee_role)` гарантирует роль исполнителя даже при административной смене роли профиля. `assignee_role` — технический фиксированный столбец, недоступный для записи клиентом.
- `task_status_history`: identity ID, задача, предыдущий/новый статус, автор перехода, время, комментарий. FK к задаче каскадный, остальные удаления ограничены.

Индексы: задачи по объекту, исполнителю, автору; история по `(task_id, id)` и автору перехода. Для истории используйте `ORDER BY id`: время само по себе не гарантирует уникальность.

## Политики RLS

Все политики ограничены `TO authenticated`; у `anon` нет прав на таблицы или RPC.

| Таблица | Политики | Доступ |
| --- | --- | --- |
| `profiles` | `profiles_read` | Свой профиль; постановщик — все; исполнитель — также профили авторов видимой ему истории |
| `construction_objects` | `objects_read` | Постановщик — все; исполнитель — объекты доступных ему задач |
| `construction_objects` | `objects_insert`, `objects_update`, `objects_delete` | Только постановщик |
| `tasks` | `tasks_read` | Постановщик — все; исполнитель — только назначенные ему |
| `tasks` | `tasks_insert` | Постановщик; автор совпадает с `auth.uid()`, статус `new` |
| `tasks` | `tasks_update`, `tasks_delete` | Только постановщик |
| `task_status_history` | `history_read` | Только если доступна соответствующая задача |

UPDATE-политика сама по себе не разрешает менять статус: GRANT UPDATE выдан только на `title`, `description`, `object_id`, `assignee_id`. INSERT тоже ограничен этими столбцами. UUID, автор, дата, статус и техническая роль исполнителя не принимаются от клиента. При запрещённом UPDATE/DELETE RLS может вернуть ноль затронутых строк, а не исключение; интерфейсу нужно это учитывать.

## Транзакции и граница доверия

1. Создание задачи и начальной записи `NULL → new`: AFTER INSERT trigger, одна транзакция.
2. Изменение статуса и история: одна RPC-транзакция. Сначала `SELECT FOR UPDATE` доступной задачи, затем сравнение ожидаемого статуса и проверка допустимого перехода, UPDATE и INSERT истории. При любой ошибке откатываются оба действия.
3. Удаление задачи и каскад истории: один DELETE. Другие транзакции не видят промежуточного состояния.
4. Переназначение и переход конкурируют за блокировку одной строки. После ожидания PostgreSQL перепроверяет строку; старый исполнитель не продолжает работу с отозванным назначением.

`transition_task(task_id, expected_status, new_status, comment DEFAULT NULL)` возвращает актуальную строку задачи. Ошибки: `42501` — нет прав/неверный переход, `40001` — устаревшее состояние (перезагрузить карточку, не повторять автоматически), `23514` — нет комментария к доработке. Несуществующая и недоступная задача дают одинаковую ошибку.

Все SECURITY DEFINER-функции имеют пустой `search_path`, квалифицированные имена и не используют динамический SQL. `current_app_role` читает только профиль `auth.uid()` и возвращает NULL без пользователя. Триггер проверяет реального постановщика и автора; RPC проверяет `auth.uid()`, роль, доступ и переход явно, поскольку владелец функции обходит RLS. EXECUTE отозван у PUBLIC/anon; пользователю доступна только RPC и функция чтения собственной роли. Триггер напрямую недоступен. Схема `private` не экспортируется PostgREST.

История автоматически создаётся триггером для новой задачи и RPC для каждой смены статуса. Отдельного API записи истории нет. При DELETE каскад выполняется внутренним FK-механизмом PostgreSQL; он не выдаёт пользователю DELETE на историю.

Администратор БД / владелец миграций — доверенная сторона, способная менять SQL и данные. Защита предназначена для `anon`/`authenticated`, а не для администратора с полномочиями PostgreSQL. Секретный серверный ключ нельзя передавать клиенту.

## Допущения

- Непустой объект удалить нельзя: сначала постановщик явно удаляет его задачи. PDF не определяет каскад объектов, поэтому массовое скрытое удаление задач не введено.
- Исполнитель обязателен и всегда имеет роль `executor`; описание может быть пустым.
- Записываем также начальное событие `NULL → new`, соответствующее строке создания в таблице переходов PDF.
- Любой постановщик управляет всеми задачами, включая созданные другим постановщиком.
- Постановщик может менять описательные поля, объект и исполнителя в любом статусе; статус при этом не сбрасывается. PDF не устанавливает дополнительных ограничений редактирования.
- После переназначения прежний исполнитель теряет доступ к задаче и её истории; новый получает всю её историю.
- Отображаемые имена участников видимой истории доступны исполнителю, email и данные Auth не публикуются.
- Удаление Auth-пользователя, который связан с профилем/задачами/историей, ограничено. Управление пользователями не является пользовательской функцией CRM.
- Настройка Auth в `config.toml` локальная. При будущем облачном развёртывании регистрацию нужно отдельно отключить в Supabase; SQL-миграция не меняет hosted Auth settings.

## Воспроизводимые проверки

`npm run db:test` запускает pgTAP с переключением реальной SQL-роли на `authenticated`/`anon` и JWT subject тестового пользователя. Fixtures создаются владельцем БД; проверки доступа исполняются пользовательской ролью. Все данные откатываются.

`npm run db:test:concurrency` использует три соединения, ждёт подтверждённой блокировки через `pg_blocking_pids`, затем проверяет конкурирующие переходы, переназначение и удаление. Данные уникальны для запуска и удаляются в `finally`. Допускается только локальный адрес БД.

`npm run db:test:api` создаёт временные Auth-аккаунты с уникальными случайными паролями, проверяет вход, закрытую регистрацию и прямые REST/RPC-запросы с реальными JWT. Служебный локальный ключ CLI используется только для подготовки/удаления аккаунтов, не для проверяемых пользовательских запросов; он не сохраняется и не печатается. После запуска fixtures удаляются.

Эти проверки не заменяют будущую проверку интерфейса и полного приложения на этапе 3.
