# Этап 3 — Integration & End-to-End Testing

Дата проверки — 5 ноября 2026. Локальный Supabase, Node 24.13.0, настоящий Google Chrome через Playwright. База не сбрасывалась. Production-окружение не использовалось.

## Воспроизводимый запуск

```sh
npm ci
npm run db:start
npx supabase migration up --local
npm run test:e2e
```

Требуется установленный Google Chrome. Playwright запускает отдельный Vite на 127.0.0.1:5174. Если порт занят, запуск останавливается, чтобы не тестировать случайный сервер. E2E выполняются последовательно с подготовкой данных перед полным запуском. Отдельный тест можно повторить через `npx playwright test --grep 'название'`, если его предусловия уже подготовлены.

`npm run demo:prepare` создаёт или находит четыре аккаунта через локальный Auth Admin API, сохраняет случайные пароли до вызова Auth и повторно использует их и восстанавливает три выделенных демообъекта. Имена аккаунтов — manager1, manager2, executor1, executor2; email имеет вид `manager1@construction-demo.test`. Идентификаторы объектов и задач постоянные. Повторные запуски не создают новые копии. Подготовка восстанавливает только три задачи с фиксированными ID независимо от их текущего объекта. Остальные задачи, в том числе добавленные в демообъекты вручную, сохраняются. Демоназвания и адреса трёх объектов восстанавливаются. Состояния задач создаются через существующий RPC.

Credentials записываются через временный файл и rename до изменения Auth; при повторе после сбоя используются те же пароли. Локальные пароли находятся в `.local/demo.json` с правами 0600. `.local/` исключён из Git. Служебный ключ читается из CLI в память и применяется только для подготовки Auth. Пользовательские API-проверки выполняются с реальными JWT постановщика/исполнителя. Скрипт также настраивает `.env.local` для локального публичного API. Эти файлы и отчёты Playwright не публикуются.

## Обнаруженные проблемы и исправления

1. Первый запуск E2E встретил занятый порт 5173. Для изолированного тестового frontend выделен 5174.
2. SQL-набор считал все записи в базе и предполагал отсутствие демоданных. Счётчики ограничены тестовыми идентификаторами, отрицательные проверки чужих записей сохранены. Набор прошёл на заполненной базе без очистки пользовательских данных.
3. Проверка сетевой ошибки ожидала ответ 5 секунд, хотя Supabase и TanStack Query продолжают автоматические повторы. Браузер оставался в loading. Ожидание этой ошибки увеличено до 30 секунд; отдельный повтор подтвердил ошибку и восстановление. Проверки приложения не отключались.
4. Vitest мог обнаруживать Playwright-файл. Его область поиска теперь явно ограничена frontend unit/component tests, E2E запускаются отдельной командой.

5. Review выявил, что перенесённая демозадача мешала повторной вставке, а смена паролей до записи credentials оставляла старый файл при сбое. Восстановление теперь идёт по ID; пароли сохраняются до Auth и повторно используются. Реальный тест переносит задачу, дважды запускает подготовку, проверяет сохранение посторонней задачи и вход всех четырёх пользователей. Три отдельные проверки имитируют ошибки БД, Auth и диска.
6. Очистка сценария A выполнялась только в успешной ветке. Теперь временный объект получает уникальное имя, а очистка его задач и самого объекта выполняется в `finally`, включая сбой до получения ID через UI. Регрессионный тест дважды создаёт записи, намеренно прерывает работу и проверяет отсутствие объекта, задачи и истории в БД.
7. Переназначение проверялось только новым входом прежнего исполнителя. Теперь его сессия открывает задачу заранее, затем выполняет reload и проверяет отказ, отсутствие заголовка и истории; новый исполнитель получает доступ.

Очистка через `finally` не гарантируется при принудительном завершении процесса (SIGKILL) или недоступной БД. Уникальные имена предотвращают неоднозначность локаторов при следующем запуске, но оставшиеся записи в таких случаях требуют адресной очистки. Пароли сохраняются локально до Auth; ошибка Auth может оставить незавершённую подготовку аккаунта, которую завершает повтор команды. Браузерные/API-тесты по-прежнему выполняются с пользовательскими JWT, служебные операции ограничены подготовкой/очисткой.

В выполненных бизнес-сценариях новых дефектов приложения не обнаружено. Изменения этапа относятся к воспроизводимости и покрытию проверок.

## Audit и bundle

В приложении эта цепочка не исполняется; риск относится к инструментам разработки и CI при работе с недоверенными шаблонами/репозиториями. Проверка production-зависимостей дала ноль. Совместимый dry-run обновлений на первоначальном прогоне ничего не предложил; при исправлении P2 повторены npm audit и production audit без изменения зависимостей. Force предлагает смену основных инструментов на другие версии; она не выполнялась.

Основной JS — около 682 КБ, gzip около 200 КБ. Браузерные сценарии на локальном соединении прошли. Предупреждение Vite зафиксировано; изменения разделения bundle не делались. Время загрузки на медленной сети и web vitals не измерялись.

## Ручная проверка

1. Выполните `npm run demo:prepare`, затем `npm run dev`. Возьмите email и пароль из `.local/demo.json`.
2. Войдите как manager1. Откройте «Демо Северный», создайте задачу для executor1, проверьте начальную историю, отредактируйте описание.
3. В отдельном профиле браузера войдите как executor1. Откройте «Мои задачи», возьмите задачу в работу и отправьте на проверку.
4. Под manager1 верните её на доработку с комментарием. Под executor1 повторно отправьте на проверку; под manager2 примите.
5. Под executor2 откройте URL чужой задачи и чужого объекта — ожидается состояние недоступности.
6. В двух профилях manager1/manager2 откройте один редактор. Сохраните изменения в первом, затем во втором — ожидается конфликт. Аналогично проверьте старое подтверждение удаления.
7. Для удаления объекта сначала удалите или перенесите задачи. При удалении задачи подтвердите удаление вместе с историей.

Повторная подготовка демо сохраняет пароли и восстанавливает исходные состояния трёх задач. Для входа используйте `.local/demo.json`. Одновременный запуск нескольких подготовок не поддерживается.

## Готовность и ограничения

Локальные функциональные и защитные сценарии подтверждены. Проект готов к подготовке деплоя после принятия этапа 3. Облачные Auth-настройки, переменные окружения хостинга, SPA fallback и работа опубликованной сборки потребуют проверки на этапе 4. Проверялся Chrome; Safari/Firefox, реальные мобильные устройства, нагрузка и полный accessibility-аудит остаются непроверенными. Сценарии выполнялись на Vite dev-сервере; production build собран, отдельный browser smoke по preview не выполнялся. Коммиты и публикация не выполнялись.
