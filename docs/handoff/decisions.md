# Решения, допущения и соответствие заданию

Источник требований — оригинальное трёхстраничное задание 2B Studio «Объекты и задачи», прочитано целиком. Уточнение заказчика о каскадном удалении истории имеет приоритет. Проверка актуальна на 05.11.2026.

## Принятые решения

1. **Роли из БД.** Один профиль имеет одну роль `manager` или `executor`; несколько пользователей каждой роли поддерживаются. Пользователь не может назначить себе роль через metadata.
2. **Общая область постановщиков.** Любой постановщик видит и управляет всеми объектами/задачами, независимо от автора. В Cloud для демонстрации один постановщик; сценарий второго проверен локально.
3. **Один исполнитель на задачу.** Назначать можно только профиль с ролью executor. Автор фиксируется при создании и не меняется при переназначении.
4. **История создания.** Создание — отдельное событие «Новая» с автором-постановщиком. Переходы выполняются только через RPC с проверкой ожидаемого статуса; других переходов нет.
5. **Комментарий.** Обязателен при возврате на доработку, пустая/пробельная строка отклоняется. На остальных переходах комментарий не обязателен.
6. **Удаление.** По уточнению заказчика задача удаляется физически вместе с историей; API напрямую менять историю не позволяет. Объект с задачами удалить нельзя — сначала задачи нужно перенести или удалить. Корзины нет.
7. **Переназначение.** Постановщик может сменить исполнителя/объект, статус сохраняется; прежний исполнитель теряет доступ при следующем запросе. Realtime не используется, обновление данных происходит при повторном запросе/переходе/перезагрузке.
8. **Конкурентность.** UUID `row_version` защищает редактирование и удаление; переходы статусов используют ожидаемый статус и блокировку строки в БД. Это дополнительная защита, согласованная отдельно.
9. **Поля.** Название и адрес объекта, название задачи обязательны; описание задачи допускает пустое значение. Даты хранятся в timestamptz и отображаются в локальном времени браузера.
10. **Небольшая архитектура.** SPA напрямую использует Supabase Auth/Data API, без дублирующего backend. Формы и экраны объединены в небольшое число файлов; UI — Tailwind/Radix и собственные компоненты.
11. **Демо.** Cloud: 1 постановщик + 2 исполнителя, 3 объекта, 3 задачи. Локальный seed изолирован от Cloud. Пароли передаются вне репозитория.

## Невыполненное и оставшиеся ограничения

- По статической сверке и ранее пройденным локальным тестам не выявлено отсутствующих обязательных функций PDF. Это не равнозначно полной проверке production под пользователями.
- Не завершён финальный production smoke с входом manager1/executor1/executor2: пароли находятся у владельца. Не отмечены пользовательские JWT-проверки Cloud и сценарий переходов в опубликованном UI. Текущая проверка production была только читающей.
- Site URL/Redirect URLs в Supabase Dashboard не проверены этим запуском. Владелец должен сверить их с production URL; для password login отсутствие redirect не заменяет проверку входа.
- Доступы и итоговое сообщение в hh.ru ещё не переданы автоматически. Это действие владельца; текстовые материалы и ссылки подготовлены.
- Полный аудит доступности, реальные мобильные устройства, Safari/Firefox, нагрузка и восстановление из резервной копии не проверены. Небольшой проект развёрнут на бесплатных тарифах без обещания непрерывной доступности.
- Предупреждение Vite: JS bundle около 682 КБ / gzip 200 КБ. Оптимизация без измеренной проблемы не проводилась. На предыдущей проверке npm audit: 9 moderate в dev-цепочке линтинга, 0 production; в финальном документировании audit повторно не запускался.
- Уведомления, файлы, сроки/приоритеты, поиск, саморегистрация и восстановление пароля в UI не входят в функциональные требования PDF и не добавлены.
- PDF ориентирует на 2–3 часа и сдачу через hh.ru. Фактическое затраченное время здесь не подтверждается; обязательства о сроках/оплате и сообщение работодателю остаются у автора. Не заявляем соблюдение временного лимита без учёта времени.
